# 技术架构与控制流

## 原则

模型可替换，数据默认留在国内，决策必须是可控状态机。大模型只负责节点内的理解、解释和策略草案；流转、权限、是否真正执行，由工作流引擎决定。

## 控制流（必须守住，框架可替换）

最优的不是“必须用 LangGraph”这个品牌，而是：**状态机 + 人在回路 + 可中断 + 可回滚 + 全程留痕**。本轮用 LangGraph 实现这条链路；若运行环境安装受限，必须实现节点名称和语义等价的状态机，以便后续无痛切回 LangGraph。

标准决策链路：

`采集 Collect → 信号 Signal → 分析 Analysis → 策略 Strategy → 人工确认 Human Review → 执行 Execute → 经验沉淀 Memory → 复盘/回滚 Rollback`

约束：

- 每个节点有明确输入、输出和失败处理
- 调价、评价回复等关键动作必须经过人审节点，默认不得自动执行
- 流程可中断、可回滚，每次状态变更写入审计日志（谁、何时、依据、结果）
- 模型不得自行决定下一步跳到哪个节点

## 系统分层（本轮落地）

- 前端展示层：Vue 3 网页管理台（中文）
- API 层：FastAPI
- 业务与控制层：工作流引擎 + 领域服务（看板、预警、定价建议、评价、对话）
- 模型层：统一模型网关（见《模型网关规则》）
- 数据层：SQLite + SQLAlchemy（便于本地跑通，结构按可迁 PostgreSQL 设计）
- 数据源：OTA 适配器接口；本轮用“携程模拟适配器 + 演示数据”，预留真实平台适配器位置

## 国内落地约定

- 生产主链路只走国产模型；境外模型仅预留适配器，默认关闭
- 云部署默认国内云多租户（本轮先把应用跑在可本机启动的环境，不绑定某一云厂商）
- 密钥只放服务端，调用留审计


## 与总体规划对齐的实现细节

节点名使用：`data_node`、`signal_node`、`analysis_node`、`strategy_node`、`human_review`、`execution_node`、`memory_node`。`memory_node` 在执行结束或人审否决后写入本店经验，并同时沉淀匿名行业模式；已执行的调价或活动会在采集后对照决策时基线做观察复盘（不是因果收入，也不是同比）。本店记忆仍按酒店隔离，L5 跨店学习只做匿名模式引用。第四增量已接通本店知识图谱、离线强化学习与默认关闭的进化引擎；一键迁移仍不开放。进化引擎不会跳过人审，不会自动改价，也不会改为线上写入。

工作流需支持 Checkpoint（决策可回放）与执行前快照；回滚使用 `checkpoint_id` 恢复执行前状态并写审计。

`OIROState` 至少包含：`hotel_id`、`hotel_profile`、`ota_snapshot`、`competitor_data`、`signals`、`analysis_result`、`strategy`、`risk_level`（low/medium/high）、`execution_result`、`approval_status`、`checkpoint_id`、`historical_memories` / `historical_strategies`（仅本店已沉淀的决策；结果影响只在事后对照决策时基线观察，不编造同比或因果收入）。

条件边（按风险等级分流到自动执行）只预留，不在 MVP 启用。MVP 中所有调价与评价回复都进入 `human_review`。

界面需能追溯一次决策经过的节点路径。
