# 总体规划融合说明

本文吸收用户补充的《OIRO × LangGraph 项目开发落地总体规划》。总体判断：这份规划对阶段划分、状态结构、检查点和决策路径可视化很有参考价值，应融合；其中部分执行策略和商业表述与已定原则冲突，本轮不采用。

## 采纳并立即并入 MVP

- 用「状态驱动的多 Agent 决策系统」来表述产品技术本质，而不是聊天机器人加数据看板
- LangGraph 节点命名与职责：`data_node` → `signal_node` → `analysis_node` → `strategy_node` → `human_review` → `execution_node` → `memory_node`（本店经验沉淀、匿名跨店学习和决策后观察复盘已接通；不做一键迁移，也不把观察变化写成因果收入）
- 明确的 `OIROState` 字段：酒店画像、OTA 快照、竞对、信号、分析结果、策略、风险等级、执行结果、审批状态、历史策略
- Checkpoint：决策可回放、执行前快照、回滚绑定 `checkpoint_id`
- 信号类型先落地三类：排名下跌 `rank_drop`、转化异常 `conversion_drop`、价格倒挂 `price_inversion`
- 界面增加「决策路径追溯」，能看到一次策略经过了哪些节点
- 风险等级 `low/medium/high` 作为策略元数据展示，并写入审计
- 数据表语义对齐：酒店、OTA 快照、策略执行记录（含审批人和检查点）；长期记忆表按酒店记录本店决策片段，并可对照决策时基线观察变化；跨店学习只引用匿名行业模式，不展示可识别复盘数字，也不迁移其他酒店身份

## 采纳但放到后续阶段，本轮不做

- 阶段 II（进行中）：风险分级后的部分自动执行（日常微调自动、波动 >15% 或节假日必须人审）、自动执行占比目标、真实 OTA 写接口。第一增量已落地可选低风险自动执行（默认关闭）和官方沙盒写回执；真实出站写入、对账、失败重试和美团/飞猪仍待后续增量。
- 阶段 III：多租户独立 Graph、PostgreSQL Checkpointer、Celery、K8s、100+ 酒店并发
- 阶段 IV：本店 Memory Node、匿名跨店学习、决策后观察复盘、本店知识图谱、离线强化学习与默认关闭的进化引擎均已交付（观察变化不是因果收入或同比；引擎只做本店建议，不跳过人审，不自动改价）；一键迁移策略仍不开放
- 小程序、真实携程/美团 API、Rate Checker、可单独售卖的轻量 / Mock PMS（官方 PMS/CRS API 预留接入已由运维端可配置，酒店画像里仍可有静态房量字段；本增量不内置房态工作台）

## 本轮明确不采用或先不改已定原则

- **关键动作自动执行**：第一阶段必须人审。第二阶段第一增量允许酒店显式开启自动执行，且仅低风险、通过节假日与调价幅度硬规则的方案可跳过等待；评价回复本增量仍必须人审。未开启时行为与第一阶段相同。
- **爬虫采集**：数据层继续用模拟适配器，不写爬虫。
- **商业模式写成「SaaS + 收益分成」**：已定主模式是订阅制（约等于传统运营人力成本的 5%–10%）。分成可作为后期选项，不写进本轮产品与收费叙事。
- **阶段 II 标价 ¥2000–5000/月/酒店**：与早期文档里的年费方案不一致，收费数字待校准，本轮不做计费模块。
