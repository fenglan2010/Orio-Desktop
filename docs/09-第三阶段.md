# 第三阶段

第三阶段要让系统从「单店演示」走向可运营的多酒店产品：真实租户隔离、PostgreSQL 与生产检查点、更完整的执行与观测。本文件按增量记录已交付范围。前四增量（租户隔离、PostgreSQL 与持久化检查点、任务队列、可复制部署）已交付。计费、爬虫、可单独售卖的轻量 PMS 或评价回复自动发布尚未开始。官方 PMS/CRS API 预留接入已由运维端可配置，默认不预装生产契约。第四阶段第一、第二增量（本店 Memory Node 与匿名跨店学习）见《第四阶段说明》。

## 第一增量：真实多酒店租户隔离（已交付）

- 用户通过 `hotel_memberships` 加入酒店。角色记在成员关系上；本增量每个演示账号只属于一家酒店。
- 登录签发的 JWT 带有 `hotel_id`。`/api/auth/me` 与 `current_hotel` 按成员关系解析当前酒店，不再硬编码 `Hotel.tenant_key == "demo"`。若请求带 `X-Hotel-Id` 或登录体带 `hotel_id`，仅当该用户是该店成员时才生效。
- 看板、预警、策略、评价、写入账本、渠道、执行策略、价格约束、审计、对话、账号和官方契约均按当前酒店过滤。用酒店 A 的令牌读取或改写酒店 B 的实体会得到 404 或 403，列表也不会混入另一家店的数据。官方契约由运维端按酒店安装，酒店账号不能互相或自行安装契约。
- 原先全局的 `SystemSetting` 键（`execution_policy`、`official_contract_*`）改为 `hotel:{id}:...`。旧键在启动时迁移到杭州演示酒店，不会让成都店继承。
- LangGraph / 等价状态机的 `thread_id` 为 `hotel-{hotel_id}-run-{run_id}`，检查点仍带 `hotel_id`，两家酒店不能互相恢复或回滚对方的图。
- 演示酒店：
  - **杭州西湖精品酒店（演示）**（`tenant_key=demo`）：`admin` / `admin123`、`manager` / `manager123`、`approver` / `approver123`、`analyst` / `analyst123`。故事仍是竞对降价后的价格倒挂与一条 2 分差评。
  - **成都春熙商务酒店（演示）**（`tenant_key=demo_chengdu`）：`admin_b` / `admin123`，只能看见成都店。故事是春熙路商务酒店工作日出租率偏软、一条关于停车的 3 分评价，不是杭州故事的复制，也不编造同比或跨渠道损益。
- 两家酒店的默认执行策略仍是 `auto_execute_enabled=false`、`write_mode=sandbox`，不预装生产官方契约。演示酒店在商务开通状态机中已是 `product_enabled`，可继续登录；新的非演示酒店须合同生效并确认付款后才会开通产品权限。电子签与支付供应商尚未接通。
- 酒店设置页继续不展示模型路由、密钥或境外开关。本增量不为单店账号做酒店切换器。

## 第二增量：PostgreSQL 与持久化 LangGraph checkpointer（已交付）

- 默认本地路径仍是 SQLite：`DATABASE_URL` 未设置时使用 `sqlite:////workspace/oiro/data/oiro.db`。共享演示进程应继续跑这条路径。
- 设置 `DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/oiro`（也接受 `postgresql://` 或 `postgres://`）即切换到 PostgreSQL。同一套 `create_all` + 增量 `migrate_schema` 在两种后端上创建/补齐表并导入演示种子。本增量未引入 Alembic，以保持迁移路径简单。
- LangGraph 不再使用进程内 `MemorySaver`：
  - SQLite：检查点写在应用库旁边的 `*.langgraph.db`（例如 `data/oiro.db.langgraph.db`）。
  - PostgreSQL：使用官方 `langgraph-checkpoint-postgres`，表建在同一数据库的 `langgraph` schema 中。
  - 线程键仍是 `hotel-{hotel_id}-run-{run_id}`。进程重启后可用 `load_graph_state` 恢复待人审图状态；回滚仍绑定应用库里的 `checkpoint_id`。用另一家酒店的 id 无法恢复该线程。
- 安全：
  - 示例环境只放占位符，不提交真实密钥。`jwt_secret` 与数据库口令来自环境变量。默认演示 `JWT_SECRET` 在上云前必须更换。
  - 应用不会把带密码的 `DATABASE_URL` 打到日志或 API。如需打印连接信息，只使用脱敏后的 URL。
  - 腾讯云 TencentDB for PostgreSQL、阿里云 RDS PostgreSQL：优先走私网（VPC）地址，并在 URL 上加 `sslmode=require`。若厂商提供 CA，再用 `sslmode=verify-ca` 或 `verify-full` 并指定 `sslrootcert`。不要把测试库绑定到 `0.0.0.0` 或在无认证的情况下对外开放。
- 可选本地测试库：`bash scripts/run_test_postgres.sh start` 会在 **127.0.0.1:55432** 启动带密码的 PostgreSQL（不监听 `0.0.0.0`），然后 `source /tmp/oiro-pgtest/env.sh` 再跑 pytest。未设置 `OIRO_TEST_DATABASE_URL` 且无法启动该库时，PostgreSQL 用例会被跳过；默认 SQLite 套件始终运行。
- 连接与 checkpointer 已做成可对接云 RDS 的形态；Compose / K8s 部署见第四增量。

## 第三增量：任务队列（已交付）

- 共享任务函数（`app.jobs.tasks`）可在无 broker 的情况下同步调用：按酒店采集、扫描可重试写入、扫描未结清写入并对账。全局扫描只是逐店调用同一函数，账本按酒店落行，酒店 A 的运行不会改写酒店 B 的指标、写入任务或 `job_runs`。
- 采集语义：
  - 只有该店已安装的官方契约**真正定义了读/采集动作**（例如 `fetch_metrics`，或动作标注 `kind/type=read|ingest`），并且具备凭证与渠道授权时，才会走官方 HTTP。不会编造携程/美团/飞猪 URL，也不会把 `apply_price` 等写入动作当成采集入口。
  - 无官方采集动作（演示默认如此）：使用现有本地模拟适配器（如 `CtripMockAdapter`）做一次审计过的刷新，记录 `source=mock`、`last_ingested_at` 和条数，**不改写**杭州/成都演示故事指标，也不会自动执行策略或自动审批。
  - 契约有采集动作但缺凭证或未授权：记录原因（`missing_credentials` / `channel_unauthorized`），不出站，回退到本地模拟刷新。
  - 官方采集若契约没有把响应映射到指标字段，本增量只记录回执摘要，不擅自落库，以免编造市场数据。
- 运行时：
  - 未配置 broker 时，本地默认用独立进程：`bash scripts/worker.sh` 或 `python -m app.jobs.worker`（可用 `--once` 跑一轮）。不监听端口，也不需要 Redis。
  - 配置 `CELERY_BROKER_URL` 或 `REDIS_URL` 后，可用 Celery worker + beat 跑同一批任务。Celery 可被导入；无 Redis 时任务仍可 eager/同步执行，测试不依赖存活的 Redis。
  - 间隔可通过环境变量配置，默认偏保守：采集 1800 秒，写入重试 120 秒，对账 300 秒（重试/对账比采集更勤）。`OIRO_JOB_QUEUE=auto|local|celery|off`（`off` 时健康检查报告 `idle`）。
  - `scripts/dev.sh` 可顺带拉起本地 worker（`OIRO_DEV_WORKER=0` 可关闭）。不启动 worker 时，API 与前端仍可运行；手动重试/对账 API 保持不变。
- 持久化：`job_runs` 经现有 `create_all` + `migrate_schema` 建表，按酒店记录 `job_type`、状态、起止时间、结果/错误摘要和操作者（调度任务为 `system:scheduler`）。调度动作写入审计。`GET /api/jobs` 只返回当前酒店的最近运行，酒店 A 看不到酒店 B。
- 健康检查 `/api/health` 增加 `job_queue`（`local` / `celery` / `idle`），不返回连接串或密码。酒店设置页不展示 Redis、Celery、broker 或其它基础设施开关；L3 写入监控只显示最近采集/重试/对账和最近任务。
- 安全：日志与 API 不会打印带密码的 `DATABASE_URL` 或 broker URL。演示默认仍是 `auto_execute_enabled=false`、`write_mode=sandbox`，不预装生产官方契约，示例契约（`"example": true`）不会被自动加载。采集不是爬虫，也不会自动发布评价回复。
- 共享演示进程应继续走 SQLite，不要为了本增量改切 PostgreSQL，也不要打开 `CTRIP_WRITE_ENABLED` 或安装生产契约。

## 第四增量：可复制部署（已交付）

本增量提供 Docker Compose 与厂商中立的 Kubernetes 清单，可对接腾讯云或阿里云，但**不绑定单一厂商**，也**不会代为开通云账号或创建实例**。共享演示进程应继续走 `scripts/dev.sh` 的 SQLite 路径（127.0.0.1:5173 / 8000），不要把它改切到 Compose 里的 Postgres，也不要打开 `CTRIP_WRITE_ENABLED` 或安装生产官方契约。

### Docker Compose

文件：`docker-compose.yml`、`deploy/docker/Dockerfile.api`、`deploy/docker/Dockerfile.frontend`、`deploy/docker/nginx.conf`、`deploy/compose.env.example`。镜像以非 root 用户运行；前端为多阶段构建（Vue 构建后由 nginx 提供静态页，并把 `/api` 反代到后端，hash 路由有 SPA fallback）。

```bash
cp deploy/compose.env.example deploy/compose.env
# 填写 JWT_SECRET 与 POSTGRES_PASSWORD（不要使用 oiro-demo-secret-change-me；密码请用 URL 安全字符）
docker compose --env-file deploy/compose.env up -d --build
```

- 网页入口：http://127.0.0.1:8080 ；API 另映射在 http://127.0.0.1:18000（仅本机）。端口避开本地演示的 5173 / 8000。
- 服务：`frontend`、`api`、`postgres`、`redis`、`worker`、`beat`。它们在内部 Docker 网络中互通。
- Postgres 与 Redis **不**发布到主机端口，更不要绑到 `0.0.0.0`。
- `OIRO_ENV` 默认为 `production`，因此必须设置独立的 `JWT_SECRET`，且数据库为 PostgreSQL。
- 默认关闭境外模型与官方写入开关：`OVERSEAS_ENABLED=false`，`CTRIP_WRITE_ENABLED` / `MEITUAN_WRITE_ENABLED` / `FLIGGY_WRITE_ENABLED` 均为 false。演示种子仍可能写入空库中的两家演示酒店，执行策略默认仍是沙盒、自动执行关闭。
- API 健康检查走 `/api/health`；Postgres、Redis、前端也有健康检查。带 `restart: unless-stopped` 与较克制的资源上限。
- Compose 适用于本机或单机虚机拉起「生产形态」的栈。云上生产应优先使用同一 VPC 内的托管数据库和 Redis，而不是把 Compose 里的 Postgres / Redis 当成长期真实源。

### Kubernetes（厂商中立，附 TKE / ACK 说明）

文件在 `deploy/k8s/`：

- `base/`：`oiro-api`、`oiro-frontend`、`oiro-worker`、`oiro-beat` 的 Deployment，ClusterIP Service，Ingress 占位，ConfigMap，可选 NetworkPolicy。镜像名可通过 kustomize `images` 覆盖，不写死某一家仓库。
- 密钥：复制 `base/secret.yaml.example` 为 `secret.yaml`（已在 .gitignore 中）或用 `kubectl create secret` 写入 `JWT_SECRET`、`DATABASE_URL`、broker URL 与模型密钥。示例里只有占位符，不要提交真实值。Secret 不包含在 kustomization 中，避免仓库里必须放密钥。
- `overlays/tke/`、`overlays/ack/`：把镜像指向腾讯云 TCR 或阿里云 ACR 的占位符路径（`YOUR_NAMESPACE` / `REPLACE_TAG`）。Ingress 的域名、证书与入口类要按集群实际情况填写，清单里不编造生产域名、账号或集群地址。
- 生产应把 `DATABASE_URL` 和 Redis 指向 VPC 内的腾讯云 TencentDB / 阿里云 RDS 与托管 Redis，并使用 `sslmode=require`（如有 CA，再用 `verify-ca` / `verify-full` 加 `sslrootcert`）。TLS 在云负载均衡上终止（腾讯云 CLB、阿里云 SLB / ALB），由运营人员在控制台挂证书，本仓库不内置证书。
- `lab/` 提供实验用的集群内 Postgres / Redis，**明确标为非生产**，仅 ClusterIP，不得改为 NodePort、LoadBalancer 或对公网开放。
- 容器：`runAsNonRoot`、禁止 privileged、丢弃全部 capabilities、设置 probes 与资源请求/限制。不要把数据库或 Redis 暴露到公网。

```bash
kubectl apply -k deploy/k8s/base          # 或 overlays/tke、overlays/ack
kubectl -n oiro apply -f deploy/k8s/base/secret.yaml   # 填好占位符之后
```

### 安全与合规

- **启动守卫**：`OIRO_ENV=production`（或 `prod`）时，若仍使用演示 `JWT_SECRET`（`oiro-demo-secret-change-me`），或未配置 PostgreSQL 的 `DATABASE_URL`，进程拒绝启动，**不会**静默回退到 SQLite。本地 `scripts/dev.sh` 不设置该变量，行为不变。
- **日志**：启动日志只写 `env` 与 `database=postgresql|sqlite`。日志和 API 不会打印带密码的 `DATABASE_URL`、broker URL 或密钥。
- **密钥**：放在环境变量或云密钥托管中（可选：腾讯云密钢管理、阿里云凭据管家或 KMS）。本增量不调用某一家云厂商的密钥 API，由运营人员把值注入环境或 Kubernetes Secret。镜像层和 git 中不得存放真实密钥。
- **数据驻留**：建议部署在中国大陆地域，使酒店经营数据与模型密钥默认留在境内。境外模型适配器默认关闭；即使打开开关，`pricing_strategy` 与 `review_reply` 也绝不出境。酒店用户侧设置页仍不展示模型密钥或 Redis / Celery 等基础设施项。
- **等保 / ICP**：VPC、TLS、密钥托管和容器基线有助于安全建设，但**不能替代** ICP 备案或等保测评。本仓库不声称已通过备案或等保。
- Compose 内的 Postgres 通常无 TLS，只适合本机/单机实验。对接云 RDS 时必须启用 TLS，且不要把测试库绑到 `0.0.0.0` 或对公网开放。

### 本增量未包含

实际开通腾讯云 / 阿里云资源、官方 OTA 生产契约、ICP 备案或等保证书、计费、可单独售卖的轻量 PMS、爬虫、一键迁移策略、评价回复自动发布，以及此前记下但推迟的产品功能优化。官方 PMS/CRS API 预留接入已落地，但仍须合作方正式契约，不能当成已对接某一家 PMS 产品。第四阶段第一、第二增量（本店 Memory Node 与匿名跨店学习）已交付，见《第四阶段说明》。
